# diff — 변경 계산과 적용

## S3 — `diff(oldV, newV)` (`diff.ts`)

### 왜 필요한가
- 상태가 바뀔 때마다 DOM을 통째로 다시 만들면 입력창 포커스·스크롤·선택 상태가 사라지고 Reflow/Repaint 비용도 크다.
- 그래서 이전 VNode 트리와 새 VNode 트리를 비교해 **무엇이 바뀌었는지**만 Patch 목록으로 계산하고, 실제 DOM에는 그 목록만 적용한다. (적용은 S4의 `patch`가 맡는다)

### 설계 결정
- **순수 함수.** `diff`는 DOM을 읽지도 쓰지도 않고 입력 트리도 변형하지 않는다. 그래서 DOM 없이 객체만으로 단위 테스트할 수 있다. 테스트에서 `document`/`window`에 접근하면 에러가 나도록 막아 두고 이를 검증한다.
- **경로(path) 기반 Patch.** 각 패치는 루트에서 자식 인덱스를 따라가는 `path: number[]`를 가진다. 루트는 `[]`, 첫 번째 자식의 두 번째 자식은 `[0, 1]`이다. 실제 DOM 노드를 직접 가리키지 않으므로 diff 단계에서 DOM과 분리된다.
- **반환 순서가 곧 적용 순서.** 패치를 앞에서부터 차례로 적용해도 결과가 올바르도록 순서를 정한다.
  - 한 노드의 `PROPS`가 그 자식들의 패치보다 먼저 나온다.
  - 공통 구간의 자식은 인덱스 순으로 재귀하고, 그다음 `CREATE`(오름차순), 마지막으로 `REMOVE`를 **뒤 인덱스부터** 낸다. 앞에서부터 지우면 뒤 노드의 인덱스가 당겨져서 경로가 어긋나기 때문이다.

### 5가지 케이스
| Patch | 발생 조건 | 담는 정보 |
|---|---|---|
| `CREATE` | old에 없고 new에만 있음 (자식이 늘어남, 루트가 null→노드) | `path`(들어갈 자리 = 부모 경로 + 인덱스), `vnode` |
| `REMOVE` | old에만 있음 (자식이 줄어듦, 루트가 노드→null) | `path` |
| `REPLACE` | `type`이 다름 (`div`→`span`, 텍스트↔엘리먼트, 다른 함수 컴포넌트) | `path`, 새 `vnode` |
| `TEXT` | 둘 다 텍스트인데 내용이 다름 | `path`, 새 `text` |
| `PROPS` | 같은 `type`인데 속성이 추가·변경·삭제됨 | `path`, `set`(추가/변경된 새 값), `remove`(사라진 이름) |

- `type`이 다르면 서브트리를 통째로 새로 만들고 **자식은 비교하지 않는다.** 서로 다른 종류의 엘리먼트는 구조가 닮았을 가능성이 낮아서, 자식까지 비교하는 비용보다 새로 만드는 쪽이 단순하고 안전하다.
- `type`이 같으면 노드는 재사용하고 속성과 자식만 비교한다. 변경이 없는 노드는 패치가 없으므로 DOM 노드가 그대로 유지된다.
- 속성 변경 여러 개는 노드당 `PROPS` 하나로 합친다.

### props 비교 규칙
- 기본은 `Object.is`다.
- `style`처럼 렌더마다 새 객체가 만들어지는 **일반 객체와 배열은 내용으로** 비교한다. 참조만 비교하면 내용이 같아도 매 렌더마다 `PROPS`가 생긴다.
- **함수(이벤트 핸들러)는 참조로** 비교한다. 참조가 다르면 다른 핸들러이므로 다시 붙여야 한다.
- 속성의 선언 순서는 무시한다. `false`는 "없음"으로 합치지 않고 값 그대로 비교한다. (`disabled: true → false`는 `set`에 `false`가 담기고, 제거로 해석하는 것은 `setProp`의 몫이다)

### 한계 (의도적)
- 자식은 **인덱스 기준**으로만 짝지어 비교한다. 리스트 앞에 항목이 끼어들면 뒤의 항목이 전부 바뀐 것으로 계산된다. `key` 기반 비교와 `MOVE`는 S5에서 추가한다.
- `key`는 아직 비교하지 않는다.
