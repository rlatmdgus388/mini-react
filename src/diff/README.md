# diff — 변경 계산과 적용

## S3 — `diff(oldV, newV)` (`diff.ts`)

### 왜 필요한가
- 상태가 바뀔 때마다 DOM을 통째로 다시 만들면 입력창 포커스·스크롤·선택 상태가 사라지고 Reflow/Repaint 비용도 크다.
- 그래서 이전 VNode 트리와 새 VNode 트리를 비교해 **무엇이 바뀌었는지**만 Patch 목록으로 계산하고, 실제 DOM에는 그 목록만 적용한다. (적용은 S4의 `patch`가 맡는다)

### 설계 결정
- **순수 함수.** `diff`는 DOM을 읽지도 쓰지도 않고 입력 트리도 변형하지 않는다. 그래서 DOM 없이 객체만으로 단위 테스트할 수 있다. 테스트에서 `document`/`window`에 접근하면 에러가 나도록 막아 두고 이를 검증한다.
- **경로(path) 기반 Patch.** 각 패치는 루트에서 자식 인덱스를 따라가는 `path: number[]`를 가진다. 루트는 `[]`, 첫 번째 자식의 두 번째 자식은 `[0, 1]`이다. 실제 DOM 노드를 직접 가리키지 않으므로 diff 단계에서 DOM과 분리된다.
- **반환 순서가 곧 적용 순서.** 패치를 앞에서부터 차례로 적용해도 결과가 올바르도록 순서를 정한다.
  - 한 노드의 `PROPS`가 그 자식들의 패치보다 먼저 나온다.
  - 공통 구간의 자식은 인덱스 순으로 재귀하고, 그다음 `CREATE`(오름차순), 마지막으로 `REMOVE`를 **뒤 인덱스부터** 낸다. 앞에서부터 지우면 뒤 노드의 인덱스가 당겨져서 경로가 어긋나기 때문이다.

### 5가지 케이스
| Patch | 발생 조건 | 담는 정보 |
|---|---|---|
| `CREATE` | old에 없고 new에만 있음 (자식이 늘어남, 루트가 null→노드) | `path`(들어갈 자리 = 부모 경로 + 인덱스), `vnode` |
| `REMOVE` | old에만 있음 (자식이 줄어듦, 루트가 노드→null) | `path` |
| `REPLACE` | `type`이 다름 (`div`→`span`, 텍스트↔엘리먼트, 다른 함수 컴포넌트) | `path`, 새 `vnode` |
| `TEXT` | 둘 다 텍스트인데 내용이 다름 | `path`, 새 `text` |
| `PROPS` | 같은 `type`인데 속성이 추가·변경·삭제됨 | `path`, `set`(추가/변경된 새 값), `remove`(사라진 이름) |

- `type`이 다르면 서브트리를 통째로 새로 만들고 **자식은 비교하지 않는다.** 서로 다른 종류의 엘리먼트는 구조가 닮았을 가능성이 낮아서, 자식까지 비교하는 비용보다 새로 만드는 쪽이 단순하고 안전하다.
- `type`이 같으면 노드는 재사용하고 속성과 자식만 비교한다. 변경이 없는 노드는 패치가 없으므로 DOM 노드가 그대로 유지된다.
- 속성 변경 여러 개는 노드당 `PROPS` 하나로 합친다.

### props 비교 규칙
- 기본은 `Object.is`다.
- `style`처럼 렌더마다 새 객체가 만들어지는 **일반 객체와 배열은 내용으로** 비교한다. 참조만 비교하면 내용이 같아도 매 렌더마다 `PROPS`가 생긴다.
- **함수(이벤트 핸들러)는 참조로** 비교한다. 참조가 다르면 다른 핸들러이므로 다시 붙여야 한다.
- 속성의 선언 순서는 무시한다. `false`는 "없음"으로 합치지 않고 값 그대로 비교한다. (`disabled: true → false`는 `set`에 `false`가 담기고, 제거로 해석하는 것은 `setProp`의 몫이다)

### 한계 (의도적)
- 자식은 **인덱스 기준**으로만 짝지어 비교한다. 리스트 앞에 항목이 끼어들면 뒤의 항목이 전부 바뀐 것으로 계산된다. (S5에서 `key`가 있는 목록은 key 기반으로 비교하도록 보완했다. 아래 S5 섹션 참고)

## S4 — `patch(container, patches)` (`patch.ts`)

### 왜 필요한가
- `diff`는 "무엇이 바뀌었는가"만 계산할 뿐 DOM을 건드리지 않는다. 그 목록을 실제 DOM에 반영하는 단계가 `patch`다.
- 계산(diff)과 적용(patch)을 나눠 두면, 계산은 DOM 없이 테스트하고 적용은 jsdom에서 따로 검증할 수 있다. 같은 패치 목록을 로그에 보여주거나(S10) 하이라이트하는 데도 재사용할 수 있다.

### 동작 원리
- **container 모델.** `patch(container, patches)`의 `container`는 루트 VNode에 대응하는 DOM을 **첫 번째 자식**으로 가진 엘리먼트다. 그래서 `path []`는 `container.childNodes[0]`이고, 루트가 없던 상태(null→노드), 루트 삭제, 루트 교체도 같은 방식으로 처리된다. 루트 노드에는 "부모"가 필요하기 때문이다.
- **path 해석.** 루트에서 시작해 `childNodes[index]`를 따라 내려간다. 경로가 없으면 조용히 넘어가지 않고 에러를 던진다. diff와 DOM이 어긋났다는 신호이기 때문이다.
- **순서대로 적용.** diff가 만든 순서(PROPS → 자식 재귀 → CREATE 오름차순 → REMOVE 내림차순)를 그대로 따르면 인덱스가 밀리지 않는다. patch는 정렬을 다시 하지 않는다.

| Patch | 적용 |
|---|---|
| `CREATE` | `createDOM`으로 만들어 `parent.insertBefore(node, parent.childNodes[index] ?? null)` |
| `REMOVE` | `parent.removeChild(node)` |
| `REPLACE` | `createDOM`으로 만들어 `parent.replaceChild(new, old)` |
| `TEXT` | `Text.data = text`. 노드는 그대로 두고 내용만 바꾼다 |
| `PROPS` | `remove`는 `removeProp`, `set`은 `setProp` |

### 설계 결정
- **노드 재사용.** 변경이 없는 노드는 패치가 없으므로 같은 DOM 객체로 남는다. 속성·텍스트만 바뀐 노드도 새로 만들지 않고 제자리에서 고친다. 그래서 입력창의 **포커스, 커서, 사용자가 입력 중인 값**이 유지된다. 테스트에서 `document.activeElement`와 노드 identity로 확인한다.
- **입력값 보호.** `value`/`checked`는 property로 다룬다(S2의 `props`). diff가 `value` 변경을 내보낼 때만 덮어쓰고, 같으면 사용자가 입력한 값을 건드리지 않는다.
- **네임스페이스 이어받기.** 새 노드는 부모의 네임스페이스를 따른다. SVG 안에서 만든 노드는 SVG, `foreignObject` 안은 HTML이다. 이를 빼먹으면 `<circle>`이 HTML 엘리먼트로 만들어져 화면에 그려지지 않는다.
- **select의 value는 마지막에.** `select.value`는 일치하는 `option`이 이미 있어야 반영된다. 같은 패치 목록에서 option이 CREATE되는 경우를 위해, select의 `value` 적용만 모든 패치가 끝난 뒤로 미룬다.
- **이벤트 핸들러.** `setProp`이 이전 리스너를 떼고 새 리스너를 붙이므로, 핸들러가 바뀌어도 이전 핸들러가 남아 중복 호출되지 않는다.
- **입력 불변.** 패치 배열과 그 안의 VNode를 변형하지 않는다. 읽기 전용(`readonly Patch[]`)으로 받고, deep freeze 상태에서도 동작하는지 테스트한다.

### 한계 (의도적)
- (S4 시점) 형제 순서가 바뀐 경우(MOVE)는 다루지 않았다. S5에서 `MOVE` 패치 적용을 추가했다.
- 적용 도중 에러가 나면 이미 적용된 패치는 되돌리지 않는다. diff가 만든 패치는 항상 적용 가능해야 하므로, 에러는 DOM이 외부에서 변경되었다는 신호로 본다.

## S5 — key 기반 diff와 `MOVE`

### 왜 필요한가
- 인덱스 기준 비교는 리스트 **앞에 항목을 끼워 넣거나 순서를 바꾸면** 뒤의 항목이 전부 "내용이 바뀐 것"으로 계산된다. 항목 100개 중 맨 앞에 하나만 추가해도 TEXT/PROPS 패치가 100개 나오고, 더 나쁘게는 **DOM 노드가 엉뚱한 항목의 것이 된다.** 그러면 항목에 딸린 입력값·포커스가 다른 항목으로 옮겨 가 보인다.
- `key`는 "이 항목은 저 항목과 같은 항목이다"라는 신원이다. key로 짝을 지으면 순서가 바뀌어도 **같은 DOM 노드를 재사용**하고, 위치만 옮기면 된다.

### 동작 원리 (`diffKeyedChildren`)
형제 중 key가 하나라도 있으면 key 기반으로, 하나도 없으면 S3의 인덱스 기준으로 비교한다. 그래서 key를 쓰지 않는 기존 코드의 결과는 그대로다.

1. **식별자 만들기.** key가 있으면 `k:<key>`, 없으면 `i:<인덱스>`. 텍스트나 key 없는 엘리먼트는 자리로 짝지어진다.
2. **짝짓기.** old 식별자 → 인덱스 맵으로 new의 각 자식에 대응하는 old 자식을 찾는다.
3. **내부 변경.** 짝지어진 쌍은 기존 `diffNode`로 재귀한다. 아직 아무것도 움직이지 않았으므로 경로는 **old 인덱스**다.
4. **REMOVE.** 짝이 없는 old 자식을 뒤 인덱스부터 지운다.
5. **MOVE / CREATE.** 남은 자식의 old 순서를 `current`로 흉내 내며 new 순서대로 훑는다.
   - 살아남은 자식들의 old 인덱스를 new 순서로 나열하고 **최장 증가 부분수열(LIS)**을 구한다. LIS에 속한 노드는 이미 올바른 상대 순서이므로 **움직이지 않는다.**
   - 나머지는 "new 기준 바로 앞 형제" 뒤로 옮긴다(`MOVE`). 짝이 없는 new 자식은 같은 자리에 `CREATE`한다.
   - 그러면 MOVE 개수는 `(살아남은 노드 수) − (LIS 길이)`로 **최소**다. 맨 앞 항목을 맨 뒤로 보내면 `n-1`번 밀지 않고 MOVE 한 번이다.

### `MOVE` 패치
```ts
{ type: 'MOVE', path: [...부모, from], to }
```
- `path`는 **패치 적용 직전**의 노드 위치, `to`는 그 노드를 형제 목록에서 **뺀 목록** 기준의 도착 인덱스다. 뺀 목록 기준으로 정한 이유는 `from < to`일 때 뒤로 옮기는 노드 하나만큼 인덱스가 어긋나는 문제를 없애기 위해서다.
- `patch`는 `parent.insertBefore(node, siblings[to] ?? null)`로 적용한다. 노드를 새로 만들지 않고 옮기므로 입력값과 이벤트 리스너가 유지된다. 루트는 부모가 없으므로 MOVE할 수 없다.

### 설계 결정
- **key는 형제 안에서만 유일하면 된다.** 다른 부모 아래의 같은 key는 서로 관계가 없다.
- **key는 문자열로 바꿔 비교한다.** `1`과 `'1'`은 같은 key다. DOM에서는 구분할 수 없기 때문이다.
- **key가 바뀌면 다른 노드다.** 같은 자리여도 `REMOVE` 후 `CREATE`한다. 같은 key인데 `type`이 다르면 그 자리에서 `REPLACE`한 뒤 필요하면 이동한다.
- **key가 중복되면** 첫 번째만 짝이 되고 나머지는 새로 만들거나 지운다. 에러를 던지지 않고 결과 DOM은 항상 목표와 같게 만든다. (노드 재사용만 일부 포기한다)
- **내부 변경을 이동보다 먼저 낸다.** 그래야 내부 패치 경로가 old 인덱스 하나로 일관된다.

### 검증: 속성 기반 fuzz (`tests/diff/fuzz.test.ts`)
시드 기반 난수로 랜덤 트리를 만들어 확인한다. 실패하면 시드가 출력되어 그대로 재현할 수 있다. 비교는 `innerHTML` 문자열이 아니라 `fromDOM` 구조로 한다. patch로 속성을 추가한 노드와 처음부터 렌더한 노드는 attribute 순서만 달라질 수 있는데, 이는 의미 없는 차이이기 때문이다.

| 시나리오 | 확인하는 것 |
|---|---|
| 변형된 트리 쌍 (600) | 기존 트리를 조금씩 바꾼 쌍에서 patch 결과 == 새 트리 |
| 무관한 랜덤 트리 쌍 (400) | 완전히 다른 두 트리에서도 patch 결과 == 새 트리 |
| 이중 오라클 (200) | patch로 만든 DOM과 새로 렌더한 DOM을 `fromDOM`으로 읽어 **다시 diff하면 빈 패치.** 구조 비교와 다른 경로로 같은 사실을 확인한다 |
| 연속 patch (150 × 5단계) | 한 트리에 patch를 거듭해도 상태가 누적되어 어긋나지 않는다 |
| key 유일 목록 (300) | 양쪽에 있는 key의 **DOM 노드 identity가 유지**된다 |
| 최소 MOVE (300) | 순열에서 MOVE 개수 == `n − LIS` |
| 큰 목록 (100, 20~100개) | 위 identity·최소 MOVE를 큰 규모에서도, 삭제·생성이 섞인 상태로 확인한다. `current.indexOf` 경로를 실제로 쓰게 하는 규모다 |
| 깊은 중첩 (200, 깊이 7) | 깊은 경로에서 내부 패치와 구조 패치가 섞여도 맞다 |
| 혼합 목록 (400) | 한 목록 안에서 key 있는 항목·없는 항목·텍스트가 자식마다 섞여도 맞다 |
| type 변경 + 이동 (300) | 같은 key의 type이 바뀌면서 위치도 바뀌는 경우. type이 같은 노드만 재사용되고 바뀐 것은 새 노드가 된다 |

- 생성기는 key 중복도 일부러 만든다. 중복 key에서도 결과 DOM이 맞아야 하기 때문이다.
- fuzz는 구현을 일부러 망가뜨린 변이(LIS 제거, 삽입 위치 오류, LIS 대신 욕심쟁이 선택)를 실제로 잡는지 확인했다.

### 한계 (의도적)
- 시간 복잡도는 `current.indexOf` 때문에 형제 수 `n`에 대해 최악 O(n²)이다. 일반적인 UI 목록 크기에서는 문제가 없어 단순함을 택했다.
- DOM 노드를 옮기면 브라우저에 따라 **포커스된 요소가 포커스를 잃을 수 있다.** 노드를 재사용해도 이동하는 노드 자체의 포커스는 보장하지 않는다. (이동하지 않는 노드의 포커스는 유지된다)
- 양 끝 비교 같은 휴리스틱은 쓰지 않는다. LIS가 최소 이동을 보장하므로 별도 최적화가 필요 없다.
- **key 없는 노드(텍스트 포함)는 자리(인덱스)로 식별된다.** key 있는 항목이 목록 앞에 끼어들면 그 뒤에 있던 텍스트·key 없는 엘리먼트는 인덱스가 한 칸씩 밀려 짝이 어긋나고, 삭제 후 재생성된다. 결과 DOM은 항상 맞지만 그 노드들은 재사용되지 않는다. 입력창처럼 상태를 유지해야 하는 항목에는 key를 붙이는 것이 전제다.
